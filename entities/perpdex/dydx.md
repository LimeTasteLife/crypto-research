# dYdX v4

> A fully decentralized perpetual exchange running as a sovereign Cosmos-SDK + CometBFT app-chain (dYdX Chain), with an off-chain in-memory CLOB matched by a 60-validator active set, a protocol-as-MM vault (MegaVault), permissionless market listings via a 10k USDC sub-vault deposit, and the broadest first-party governance + parameter surface of any perp DEX surveyed.

## Snapshot
- Market structure: off-chain in-memory CLOB; validators store orders out-of-consensus and propose blocks via price-time priority on their local books[^dydx-docs-2026-04-28-concepts-architecture-overview][^dydx-docs-2026-04-28-concepts-trading-limit-orderbook]
- Operator: dYdX Trading Inc. (open-sourced the v4 software but does NOT run any of the protocol/Indexer/front-end components); dYdX Foundation; dYdX Operations subDAO; dYdX Treasury subDAO; CryptoLearningClub (manages VIP affiliates via Grants)[^dydx-community-2026-04-28-introduction][^dydx-docs-2026-04-28-concepts-architecture-overview][^dydx-community-2026-04-28-dydx-features-affiliate-program]
- Native token: [[entities/token/dydx]] (governance, staking, fee discount via 5-tier staking ladder)[^dydx-community-2026-04-28-start-here-dydx-token][^dydx-docs-2026-04-28-concepts-trading-rewards]
- Network: [[entities/network/dydx-chain]] (own Cosmos-SDK + CometBFT PoS L1, 60-validator active set, 21-day unbonding per current on-chain value)[^dydx-community-2026-04-28-introduction][^dydx-community-2026-04-28-modules-staking]
- Genesis: October 26, 2023, 17:00 UTC (block 1 produced by validators)[^dydx-community-2026-04-28-introduction]
- Listing surface: permissionless market listings via 10k USDC MegaVault sub-vault deposit (Skip-managed `launchable` set); plus governance-listed cross-margin markets[^dydx-community-2026-04-28-dydx-features-instant-market-listings][^dydx-community-2026-04-28-modules-governance-markets]

## Mechanism

**dYdX Chain (CosmosSDK + CometBFT PoS).** dYdX v4 is the Cosmos-SDK and CometBFT proof-of-stake L1 built specifically to run a perpetual DEX[^dydx-community-2026-04-28-introduction][^dydx-docs-2026-04-28-concepts-architecture-overview]. The node software is written in Go, compiles to a single binary, and was open-sourced by dYdX Trading Inc.; the protocol, Indexer, and front-ends are all open-source and dYdX Trading Inc. does not run any of them[^dydx-docs-2026-04-28-concepts-architecture-overview]. Block proposers are selected via stake-weighted round-robin; a block commits when ≥2/3 of validators (by stake weight) approve[^dydx-docs-2026-04-28-concepts-architecture-overview]. The Indexer is a read-optimized Postgres + Redis + Kafka stack consuming from full nodes — separating query load from consensus[^dydx-docs-2026-04-28-concepts-architecture-overview]. The first block was produced on October 26, 2023, 17:00 UTC[^dydx-community-2026-04-28-introduction].

**Off-chain CLOB with in-memory order books.** Each validator/full-node holds an in-memory order book that mutates in real time as traders submit instructions; cancels are stored until they expire by Good-Til-Block (GTB)[^dydx-docs-2026-04-28-concepts-trading-limit-orderbook]. Block proposers build blocks from their local book using price-time priority; books may diverge across nodes intra-block, then sync to the just-committed block state[^dydx-docs-2026-04-28-concepts-trading-limit-orderbook]. Orders split into two lifetimes: short-term (in-memory, ≤20-block GTB ≈ 30s, intended for MMs and market orders, best-effort cancel-by-gossip) and stateful (long-term + conditional, on-chain, GTBT up to 95 days)[^dydx-docs-2026-04-28-concepts-trading-orders]. Six order types — Market, Limit, Stop Market, Stop Limit, Take Profit Market, Take Profit Limit — plus TWAP added in v9.0 (OrderFlags=128)[^dydx-docs-2026-04-28-concepts-trading-orders]. The CLOB module schema represents each market as a Clob Pair (Perpetual / Spot / other)[^dydx-community-2026-04-28-modules-governance-clob]. See [[concepts/operations/matching-engine]] and [[concepts/market-structure/clob]].

**OEGS (Order Entry Gateway Service).** OEGS is the next-stage performance evolution shipping in two parts: Designated Proposers (a governance-selected validator subset that proposes blocks, available in v9) and the OEGS gateway nodes (peer directly with all designated proposers, accept orders via public gRPC, bypass standard gossip in a single hop)[^dydx-docs-2026-04-28-concepts-architecture-oegs][^dydx-docs-2026-04-28-concepts-architecture-overview]. The motivating problem is that previously professional trading firms had to run private full nodes with streaming enabled to inject orders directly into gossip for competitive latency; OEGS lowers that barrier and is fully opt-in (traders may still submit via any full node)[^dydx-docs-2026-04-28-concepts-architecture-oegs]. dYdX Labs plans to fully open-source OEGS code; governance may consider operator incentives[^dydx-docs-2026-04-28-concepts-architecture-oegs]. dYdX claims a 98% improvement in API performance/reliability since April 2025[^dydx-docs-2026-04-28-concepts-architecture-oegs]. OEGS is now live on testnet[^dydx-docs-2026-04-28-concepts-architecture-overview].

**Fee tiers and staking discount ladder.** Fees are uniform across markets and tiered by 30-day trailing volume across sub-accounts and markets[^dydx-community-2026-04-28-modules-governance-fee-tiers][^dydx-docs-2026-04-28-concepts-trading-rewards]. The published rate card runs 7 tiers from <$1M (5.0bps taker / 1.0bps maker) up to ≥$200M (2.5bps taker / −1.1bps maker rebate)[^dydx-docs-2026-04-28-concepts-trading-rewards]. Staking-DYDX fee discounts overlay the tier ladder in 5 tier groups, each with two discount levels (e.g. tier 1 = 25% at 3,000 DYDX or 50% at 20,000 DYDX, scaling to tiers 5–7 = 5% at 800,000 or 10% at 5,000,000 DYDX); discounts apply only to net positive trading fees and only count bonded DYDX (no discount on rebates, no credit for unbonding stake)[^dydx-docs-2026-04-28-concepts-trading-rewards]. Fee tier updates are governance-driven via `MsgUpdatePerpetualFeeParams`; the Stats Module tracks user maker/taker volumes over a 30-day look-back window (governance-adjustable in seconds)[^dydx-community-2026-04-28-modules-governance-fee-tiers][^dydx-docs-2026-04-28-concepts-trading-governance]. See [[parameters/dydx-v4/fee-schedule]].

**Funding rate.** Funding has two epochs: funding-sample (default 60s, samples premium via median FundingPremiumVote, min_num_votes_per_sample = 15) and funding-tick (default 3,600s, averages 60 samples)[^dydx-community-2026-04-28-modules-governance-perpetual][^dydx-docs-2026-04-28-concepts-trading-funding]. Premium = (max(0, ImpactBid − Index) − max(0, Index − ImpactAsk)) / Index, where Impact Notional = 500 USDC / IMF[^dydx-docs-2026-04-28-concepts-trading-funding]. Final funding rate = (Premium / 8) + Interest Rate Component; cross markets use 0% IRC by default, isolated markets use 0.125 bps/h (1 bps/8h) per governance vote 220[^dydx-docs-2026-04-28-concepts-trading-funding]. The 8-hour rate cap = 600% × (IMF − MMF), giving 12%/8h for Large-Cap (IMF=5%, MMF=3%); funding_rate_clamp_factor_ppm = 6,000,000 (6%) and premium_vote_clamp_factor_ppm = 60,000,000 (60%) per the Perpetual module[^dydx-docs-2026-04-28-concepts-trading-funding][^dydx-community-2026-04-28-modules-governance-perpetual]. Funding payments are exchanged directly between traders, not the exchange[^dydx-community-2026-04-28-modules-governance-perpetual]. See [[parameters/dydx-v4/funding-config]].

**Oracle (Slinky / vote-extension validator sidecars).** Oracle prices are aggregated by validator-run sidecars (Slinky) pulling from external exchanges including Binance, Bitfinex, Bitstamp, Bybit, Coinbase, crypto.com, GateIO[^dydx-docs-2026-04-28-concepts-trading-oracle]. Each validator submits its view via vote extensions; the proposer aggregates and proposes; the network accepts the block; oracle prices update — all in-consensus[^dydx-docs-2026-04-28-concepts-trading-oracle]. Oracle update flow is rate-limited by a max-markets-per-block ceiling and a min-price-change threshold[^dydx-docs-2026-04-28-concepts-trading-oracle]. Per-market oracle parameters (`min_exchanges`, `min_price_change_ppm`, `exchange_config_json`) are governance-adjustable; adding/removing supported source-exchanges requires a binary upgrade[^dydx-community-2026-04-28-modules-governance-markets][^dydx-docs-2026-04-28-concepts-trading-governance]. Oracle Price (not last-traded) drives liquidation eligibility and stop/take-profit triggers[^dydx-docs-2026-04-28-concepts-trading-liquidations]. See [[parameters/dydx-v4/oracle-config]].

**Margin and Liquidity Tiers.** Each market has two risk parameters: IMF (initial margin fraction, may scale with OI) and MMF (maintenance margin fraction, fixed)[^dydx-docs-2026-04-28-concepts-trading-margin]. The Open-Interest-scaled IMF formula: `effective_IMF = min(base_IMF + max(scaling_factor × (1 − base_IMF), 0), 1.0)` where `scaling_factor = (open_notional − lower_cap) / (upper_cap − lower_cap)` — at upper_cap or above, IMF reaches 100% (1:1 collateral)[^dydx-docs-2026-04-28-concepts-trading-margin][^dydx-docs-2026-04-28-concepts-trading-governance]. MMF does not scale with OI[^dydx-docs-2026-04-28-concepts-trading-margin]. Free collateral = TAV − Total IMR; an account becomes liquidatable when TAV < Total MMR[^dydx-docs-2026-04-28-concepts-trading-margin]. The Liquidity Tier table covers 8 tiers (Large-Cap 0, Small-Cap 1, Long-Tail 2, Safety 3, Isolated 4, Mid-Cap 5, FX 6, IML 5x 7); the per-tier (IMF, MMF, capacity) values appear in two divergent forms across docs — the community-docs `MsgUpdateMarketParam`-style schema uses `base_position_notional` + `impact_notional`, while the docs.dydx.xyz governance page uses `lower_cap` / `upper_cap` and gives different numeric values for impact_notional (Tier 0 = 25,000 USDC vs 10,000 USDC) — see [[#dispute-liquidity-tier-schema]][^dydx-community-2026-04-28-modules-governance-markets][^dydx-docs-2026-04-28-concepts-trading-governance]. See [[parameters/dydx-v4/margin-tiers]].

**Isolated Markets (v5.0.0).** Isolated Markets shipped in v5.0.0: each isolated market gets its own segregated collateral pool and insurance fund, and a subaccount holding an isolated position cannot open positions in any other market until the isolated position is closed (orders for other markets fail with error 2005 at match time)[^dydx-docs-2026-04-28-concepts-trading-isolated-markets]. To accommodate one subaccount per isolated market, the per-address subaccount limit was raised from 127 to 128,000 in v5.0.0[^dydx-docs-2026-04-28-concepts-trading-isolated-markets]. `PerpetualParams.market_type` is the on-chain switch (`PERPETUAL_MARKET_TYPE_CROSS` is the default and applies to all pre-v5.0.0 markets; `PERPETUAL_MARKET_TYPE_ISOLATED` is the new option)[^dydx-docs-2026-04-28-concepts-trading-isolated-markets]. Recommended criteria for upgrading an isolated market to cross: ≥2 oracle sources each with >$1M USD volume, ≥2 sources with >$150K depth within 2% of mid, ≥4 total oracle sources, ≥30 days of historical data[^dydx-community-2026-04-28-modules-governance-markets].

**Liquidations and contract-loss waterfall.** Accounts with TAV below MMR may be auto-liquidated — the engine generates a liquidation order at a calculated Fillable Price as the limit, which is matched against book liquidity[^dydx-docs-2026-04-28-concepts-trading-liquidations]. Default Maximum Liquidation Penalty = 1.5% (governance-adjustable; 100% of the fee goes to the Insurance Fund)[^dydx-docs-2026-04-28-concepts-trading-liquidations][^dydx-docs-2026-04-28-concepts-trading-governance]. The Insurance Fund covers insufficient collateral by widening the limit price up to a max spread from oracle (default 1.5 × MMF, e.g. 4.5% for a 3% MMF market)[^dydx-docs-2026-04-28-concepts-trading-contract-loss-mechanism]. Once an account's value turns negative, deleveraging fires immediately against randomly chosen offsetting positions — the IF is bypassed at this stage[^dydx-docs-2026-04-28-concepts-trading-contract-loss-mechanism]. Isolated-market positions are handled by that market's segregated insurance fund; cross-market positions share a single IF[^dydx-docs-2026-04-28-concepts-trading-contract-loss-mechanism][^dydx-community-2026-04-28-modules-governance-markets]. Liquidation price formulae: isolated `p' = (e − s × p) / (|s| × MMF − s)`; cross subtracts other-position MMR[^dydx-docs-2026-04-28-concepts-trading-liquidations]. The actual close price is the maker-side fill (can be better than the fillable-price limit)[^dydx-docs-2026-04-28-concepts-trading-liquidations]. See [[concepts/risk/liquidation]] and [[concepts/risk/adl-waterfall]].

**MegaVault (protocol-as-MM).** MegaVault is dYdX's protocol-as-MM construct: USDC depositors fund automated AMM strategies running across per-market sub-vaults, with deposits representing fractional ownership of the vault's net equity (USDC + active positions)[^dydx-docs-2026-04-28-concepts-trading-megavault][^dydx-community-2026-04-28-dydx-features-megavault]. Yield comes from PnL on vault positions, funding payments, and a 50% trading-fee revenue share (community-approved Nov 15, 2024; governance-adjustable)[^dydx-community-2026-04-28-dydx-features-megavault]. Greave was elected MegaVault operator on November 21, 2024, with authority to tune sub-vault parameters and reallocate capital[^dydx-community-2026-04-28-dydx-features-megavault]. APR formula: `(30d PnL / current TVL) × (365/30)` — and APR will likely decrease as TVL grows because more depositors share fee/PnL flow[^dydx-community-2026-04-28-dydx-features-megavault]. MegaVault uses cross-margined funds, has no general lock-up except for Instant Market Listings (~30-day lock at 1s avg block time), and the docs flag depositors can lose money — published worst-case withdrawal slippage is 100% (full loss) at 8x leverage[^dydx-community-2026-04-28-dydx-features-megavault]. US/Canada/prohibited-jurisdiction users excluded[^dydx-community-2026-04-28-dydx-features-megavault]. See [[parameters/dydx-v4/megavault]].

**Instant Market Listings (permissionless).** Users can permissionlessly list a perpetual market by depositing 10,000 USDC into the new asset's MegaVault sub-vault — no governance vote required[^dydx-community-2026-04-28-dydx-features-instant-market-listings]. Funds are locked for 2,592,000 dYdX blocks (~30 days at 1s avg block time, but actual could be longer)[^dydx-community-2026-04-28-dydx-features-instant-market-listings]. Skip is the dYdX-elected Market Map Updater that maintains the on-chain `launchable` asset set; coverage spans most assets from Base, Ethereum, Solana, and CEXs[^dydx-community-2026-04-28-dydx-features-instant-market-listings]. The 10k USDC and 30-day lock-up are governance-adjustable parameters; deposited funds are NOT principal-protected — they sit in MegaVault and bear MM trading risk[^dydx-community-2026-04-28-dydx-features-instant-market-listings]. Governance-listed markets follow the longer 4-message path: `MsgCreateOracle → MsgCreatePerpetual → MsgCreatePerpetualClobPair → MsgDelayMessage` (to schedule `MsgSetClobPairStatus` enabling trading)[^dydx-docs-2026-04-28-concepts-trading-governance]. US/Canada users explicitly prohibited[^dydx-community-2026-04-28-dydx-features-instant-market-listings]. See [[parameters/dydx-v4/listing-policy]].

**A3 mechanism #1 — Order Router Rev Share.** Third-party order routers earn a portion of trading fees (maker AND taker) by including their `order_router_address` in the order message; the share (in ppm) is set per-router by governance proposal (`/dydxprotocol.revshare.MsgSetOrderRouterRevShare`, with `address` and `share_ppm` fields; example: 500,000 = 50%)[^dydx-community-2026-04-28-modules-governance-order-router-rev-share][^dydx-docs-2026-04-28-interaction-integration-revshare]. Revenue distributes based on filled orders routed through that router[^dydx-docs-2026-04-28-interaction-integration-revshare]. **Affiliate priority rule:** if an active affiliate split has not reached its $10k/30d-rolling-window cap, no revenue is shared with the order router[^dydx-docs-2026-04-28-interaction-integration-revshare]. Router activity is observable via the indexer's `/orders` (router address) and `/fills` (router address + per-fill revenue) endpoints[^dydx-docs-2026-04-28-interaction-integration-revshare]. The reference governance proposal cited in docs is dYdX proposal 311[^dydx-docs-2026-04-28-interaction-integration-revshare]. Will be filed in Phase 2.2 as [[entities/programme/dydx-order-router-rev-share]] (forward-ref).

**A3 mechanism #2 — Affiliate Program.** Lifetime-commission model with on-chain USDC payouts, two tiers: VIP (≤50% of referred user taker fees, $10,000/referral/30d cap) and Standard (≤15% taker fees, $3,000/referral/30d cap)[^dydx-community-2026-04-28-dydx-features-affiliate-program]. Volume gate: $10,000 in trading volume required before the affiliate link unlocks (achievable with leverage)[^dydx-community-2026-04-28-dydx-features-affiliate-program]. Commissions pay instantly and automatically on-chain in USDC[^dydx-community-2026-04-28-dydx-features-affiliate-program]. The dYdX Grants Program onboarded CryptoLearningClub to manage the VIP tier — they regularly submit on-chain proposals to whitelist new VIPs and remove underperformers[^dydx-community-2026-04-28-dydx-features-affiliate-program]. VIP eligibility requires a track record in other crypto affiliate programs, ≥30,000 genuine social-media followers, and notable social influence; professional MMs and trading firms are excluded[^dydx-community-2026-04-28-dydx-features-affiliate-program]. Will be filed in Phase 2.2 as [[entities/programme/dydx-affiliate-program]] (forward-ref).

**Builder Codes (third A3 surface).** Builder codes are a third A3-adjacent surface: external parties add a per-order fee on top of each fill (not a split of existing fee revenue, unlike Order Router Rev Share) by setting `BuilderCodeParameters` with `feePpm` (in (0, 10000]) and `builderAddress`[^dydx-docs-2026-04-28-interaction-integration-builder-codes]. No governance proposal is required to use builder codes; they are queryable via the indexer's `/orders` and `/fills` endpoints[^dydx-docs-2026-04-28-interaction-integration-builder-codes].

**Governance.** dYdX uses CosmosSDK's standard `x/gov` module with five proposal types (text, parameter change, community spending, software upgrade, new market)[^dydx-community-2026-04-28-modules-governance][^dydx-docs-2026-04-28-concepts-trading-governance]. Vote weight = actively-staked DYDX (1:1); unstaked or unbonding DYDX does not count; if a staker doesn't vote, they inherit their validator's vote[^dydx-community-2026-04-28-modules-governance]. Voting options: Yes / No / NoWithVeto / Abstain[^dydx-community-2026-04-28-modules-governance]. Current on-chain governance parameters per the community docs: min_deposit = 2,000 DYDX, max_deposit_period = 7 days, min_initial_deposit_ratio = 20%, voting_period ≈ 4 days, quorum = 33.4%, threshold = 50%, veto_threshold = 33.4%; expedited threshold = 75% with quorum 33.4% and a 1-day voting period; burn_vote_veto = True (vetoed deposits burned), burn_vote_quorum = False, burn_proposal_deposit_prevote = False[^dydx-community-2026-04-28-modules-governance]. The docs.dydx.xyz `Rewards, Fees and Parameters` page disagrees on min_deposit (10k tokens) and max_deposit_period (1 day) — see [[#dispute-governance-min-deposit]] and [[#dispute-governance-max-deposit-period]][^dydx-docs-2026-04-28-concepts-trading-rewards]. The 8-stage proposal lifecycle is Forum Discussion → DRC Creation (off-chain) → DRC Discussion (~4d) → DIP Creation → On-chain Submission → Deposits → Voting → Tallying & Execution; Parameter Change Proposals take effect in the block AFTER the voting period ends[^dydx-community-2026-04-28-modules-governance-proposal-lifecycle]. Governance can update an exhaustive surface: Stats Module look-back, FeeTiers, Insurance Fund send-out, LiquidationsConfig (max IF quantums for deleveraging, max liquidation fee ppm with 100% to IF, position/subaccount per-block liquidation caps, fillable price config), Funding Rate clamps + epoch info + Liquidity Tier impact notional, Vest/Rewards Modules (incl. constant C), Oracles per market, full Liquidity Tier table, Bridge Module enable/disable, Community Pool / Community Treasury, equity-tier order limits + rate limits[^dydx-docs-2026-04-28-concepts-trading-governance][^dydx-community-2026-04-28-modules-governance-adjustable-parameters]. See [[parameters/dydx-v4/governance-params]].

**Validators, slashing, and security.** dYdX uses the CosmosSDK `x/staking` module: max_validators = 60 (per docs.dydx.xyz Rewards page), min_commission_rate = 5%, default validator commission rate = 100%, with stake-weighted Active Set updated each EndBlock[^dydx-docs-2026-04-28-concepts-trading-rewards][^dydx-community-2026-04-28-modules-staking]. Unbonding period is currently 21 days per the community-docs Staking module — the older docs.dydx.xyz Rewards page states 30 days, see [[#dispute-unbonding-period]][^dydx-community-2026-04-28-modules-staking][^dydx-docs-2026-04-28-concepts-trading-rewards]. Slashing parameters: signed_blocks_window = 8192 blocks (~3h11m at 1.4s blocks), min_signed_per_window = 0.2 (20%), downtime_jail_duration = 7,200s (2h), `slash_fraction_double_sign = 0.0` and `slash_fraction_downtime = 0.0` — i.e. no monetary slash for either currently, but tombstoning still applies for double-sign and jailing still applies for downtime[^dydx-community-2026-04-28-modules-slashing][^dydx-docs-2026-04-28-concepts-trading-rewards]. Liveness formula: `maxMissed = signed_blocks_window − min_signed_per_window × signed_blocks_window`; jailed validators must send `MsgUnjail` to return after downtime jailing[^dydx-community-2026-04-28-modules-slashing]. MEV is acknowledged as harmful — dYdX Trading and Skip Protocol have built a dashboard surfacing validator MEV-extraction-related orderbook discrepancies — but there is no protocol-level mitigation; governance could approve a social-slashing framework[^dydx-community-2026-04-28-modules-slashing]. Validator hardware: ≥500 GiB locally-attached SSD, ≥64 GiB RAM, ≥8-core x86_64 (AWS r6id.2xlarge equivalent)[^dydx-chain-tech-2026-04-28-validators-getting-set-up-hardware-requirements]. Winding-down validators should give 45–60 days notice and notify the dYdX Operations subDAO[^dydx-community-2026-04-28-modules-staking]. The dYdX Chain protocol was audited by Informal Systems; finalized audit reports live in the v4_chain audits folder; additional audits are planned as more code ships; all core repos are public to enable community vulnerability identification[^dydx-docs-2026-04-28-policies-security][^dydx-community-2026-04-28-introduction]. See [[parameters/dydx-v4/validator-requirements]] and [[parameters/dydx-v4/audits]].

**Tokenomics, treasuries, and revenue distribution.** 1B DYDX was minted on August 3, 2021 at 15:00 UTC, vesting over 5 years[^dydx-community-2026-04-28-start-here-dydx-token-allocation]. Current allocation: 50% community (26.1% Treasury, 14.5% Trading Rewards, 5% retroactive mining, 3.3% LP Rewards, 0.6% USDC LP staking, 0.5% safety pool), 27.7% past investors, 15.3% founders/employees, 7.0% future employees[^dydx-community-2026-04-28-start-here-dydx-token-allocation]. The Trading Rewards allocation was cut by DIP 16 (−25%) and DIP 20 (−45%); LP Rewards cut via DIP 24 / DIP 29; USDC and Safety pool rewards set to 0 via DIP 14 / DIP 17; investor lockup amended Jan 25, 2023 (30% release Dec 2023, then equal monthly through June 2026)[^dydx-community-2026-04-28-start-here-dydx-token-allocation]. **Protocol Revenue Sharing** (introduced via dYdX Unlimited, August 12, 2024) lets the community adjust net-revenue allocation via `MsgUpdateUnconditionalRevShareConfig`; on November 13, 2025 the community approved 75% to the Buyback Program, 5% to Treasury SubDAO, 5% to MegaVault, 15% to the Distribution module account (validators/stakers/community pool)[^dydx-community-2026-04-28-modules-distribution-protocol-revenue-sharing]. Default community tax = 0%; WithdrawAddrEnabled = True[^dydx-docs-2026-04-28-concepts-trading-rewards]. Community Treasury (`dydx15ztc7xy42tn2ukkc0qjthkucw9ac63pgp70urn`, governance-controlled) currently receives ~2.04 DYDX/second from the Community Vester (`dydx1wxje320an3karyc6mjw4zghs300dmrjkwn7xtk`) until August 3, 2026; current per-epoch vesting rate is 3,787,251 DYDX (vs initial 766,703); DIP 29 migrated 80,492,270 DYDX from v3 Rewards Treasury + Community Treasury into the v4 Community Treasury[^dydx-community-2026-04-28-modules-community-treasury]. Spending requires a Community Spending governance proposal[^dydx-community-2026-04-28-modules-community-treasury]. See [[parameters/dydx-v4/tokenomics]] and [[parameters/dydx-v4/revenue-distribution]].

**Staking rewards.** Staking rewards source = trading fees (USDC) + gas fees (USDC + DYDX); per-block accrual in `fee_collector` → next-block transfer to `distribution` module → community_tax + validator_commission subtracted → remainder distributed proportionally by stake[^dydx-docs-2026-04-28-concepts-trading-rewards-staking-rewards][^dydx-community-2026-04-28-modules-distribution]. Stakers must claim manually; unclaimed rewards remain in the distribution module account; rewards are NOT auto-restaked[^dydx-docs-2026-04-28-concepts-trading-rewards-staking-rewards][^dydx-community-2026-04-28-modules-distribution]. Formula: `Staking Rewards = fee_pool × (delegator_stake / total_stake) × (1 − community_tax) × (1 − validator_commission)`[^dydx-docs-2026-04-28-concepts-trading-rewards-staking-rewards]. See [[parameters/dydx-v4/staking-rewards]].

**Trading Rewards (status disputed).** The docs.dydx.xyz Trading Rewards page documents a C-formula: `taker_reward = taker_volume × (taker_fee_rate − max_maker_rebate − max_affiliate_taker_fee_share) × C × (1 − protocol_revenue_share_rate)` and a parallel maker formula, with affiliate share = 0 if taker 30d volume > $50M else 50% × taker_fee_rate, and a global cap of 90% of fill's net trading fees per block[^dydx-docs-2026-04-28-concepts-trading-rewards-trading-rewards]. The same page notes inline that C is currently set to 0 (so traders get rebates directly instead of C-constant rewards)[^dydx-docs-2026-04-28-concepts-trading-rewards-trading-rewards][^dydx-docs-2026-04-28-concepts-trading-rewards]. The community-docs Trading Rewards page asserts that protocol-level trading rewards have been removed and consolidated under the Surge Program — see [[#dispute-trading-rewards-status]][^dydx-community-2026-04-28-modules-trading-rewards]. See [[parameters/dydx-v4/trading-rewards-config]] and the forward-ref [[entities/programme/dydx-surge]] (Phase 2.2).

**Compliance.** Per dYdX terms: persons in USA, Canada, Iran, Cuba, North Korea, Syria, Myanmar (Burma), or Crimea/Donetsk/Luhansk are prohibited; OFAC-sanctioned parties are prohibited; third-party integrators are expected to enforce client-side geo-blocking[^dydx-docs-2026-04-28-interaction-integration-compliance]. The indexer exposes two compliance endpoints: `/v4/geo` (returns IP-derived geo + a `blocked` boolean) and `/v4/screen/<address>` (returns per-address compliance status with reason + updatedAt)[^dydx-docs-2026-04-28-interaction-integration-compliance]. Existing investor transfer restrictions remain enforced via contractual agreements with the dYdX Foundation and dYdX Trading Inc.[^dydx-community-2026-04-28-start-here-dydx-token-allocation]. See [[parameters/dydx-v4/compliance]].

**Front-end sovereignty.** Three open-source front-ends exist (web in JavaScript/React, iOS in Swift, Android in Kotlin); the web front-end can be deployed by anyone to their own domain/hosting (including IPFS / Cloudflare gateway) and deployment scripts are open-sourced[^dydx-docs-2026-04-28-concepts-architecture-overview]. None of the protocol, Indexer, or front-end components are run by dYdX Trading Inc.[^dydx-docs-2026-04-28-concepts-architecture-overview].

## Risks

**Per-market parameter time-series only on-chain.** The wiki's per-market parameter snapshot is from the docs only; historical change series for IMF / MMF / max-leverage / OI cap per market lives on-chain (queryable via the `prices` and `perpetuals` modules) — currently a gap (G(dydx)-1). For a full per-market time-series ingest, on-chain analysis is required.

**MegaVault TVL / IF coverage ratio numerics unsourced.** Frame cell A6/PIII (IF coverage ratio = IF / (max-OI × slippage × gap%)) and the analogous MegaVault-as-MM sizing are not computed in primary docs — only the qualitative statement that depositors bear market risk and worst-case 100% slippage at 8x leverage. Operators forecasting tail risk must derive these from on-chain balances + listed-markets-roster snapshots.

**Trading Rewards documentation contradiction (live vs removed).** docs.dydx.xyz still publishes the C-formula in detail with a footnote that C is currently 0; community docs assert the protocol-level rewards are removed and consolidated into the Surge Program. Both can be simultaneously true ("formula present in code, set to 0"), but downstream consumers should not assume a non-zero C without on-chain verification of the `Rewards` module state.

**Schema-version drift (Liquidity Tier table).** Two divergent published versions of the on-chain Liquidity Tier table coexist. Numerical risk forecasting (impact-notional-driven funding premium calculation, OI-scaling IMF capacity) can produce materially different outputs depending on which version is canonical. See [[#dispute-liquidity-tier-schema]] — highest-stakes dispute on the page.

**Affiliate operator concentration.** VIP affiliate management is delegated to a single operator (CryptoLearningClub) via dYdX Grants — operator-bottleneck risk for affiliate-side onboarding/clawback. SLA template for the operator (G(dydx)-4 gap) not surfaced.

**MM-agreement template gap.** dYdX has no first-party MM-agreement template (uptime SLA, depth commitment, exclusivity, downtime compensation, orderly offboarding) per A4/PV gap (G(dydx)-3). External MMs must self-codify their economics on top of the −1.1bps tier-7 maker rebate and Order Router Rev Share routing-layer mechanics.

**MEV mitigation is dashboard-only.** dYdX docs explicitly acknowledge MEV is harmful but state there is no protocol-level mitigation; the only first-party tool is the Skip-built validator-MEV-discrepancy dashboard. Governance could approve a social-slashing framework but has not done so. Risk: validator MEV extraction is observable but not penalizable.

**Order Router Rev Share recipient list opaque.** The on-chain whitelist of approved Order Router addresses + their `share_ppm` values is queryable via on-chain governance state but not enumerated in primary docs (G(dydx)-2 gap). Downstream attribution (who actually receives router revenue) requires on-chain query.

## Asset profile — DYDX (informal; full token page in Phase 2.2)

DYDX is dYdX Chain's L1 native token, adopted by the dYdX community via Snapshot + on-chain governance[^dydx-community-2026-04-28-start-here-dydx-token]. Three documented purposes: governance (proposing/voting on changes to governable parameters, community spend, software upgrades), security (staking weight raises attack cost), and staking (delegators run validators or delegate to existing validators)[^dydx-community-2026-04-28-start-here-dydx-token]. 1B supply minted Aug 3, 2021; 5y vesting; 50% community / 27.7% past investors / 15.3% founders+employees / 7.0% future employees[^dydx-community-2026-04-28-start-here-dydx-token-allocation]. Initial transfer restrictions lifted Sep 8, 2021; investor lockup amended Jan 25, 2023 with the final 10% releasing Jul 2025–Jun 2026[^dydx-community-2026-04-28-start-here-dydx-token-allocation]. The token also drives the 5-tier-group fee discount on dYdX v4 (25–50% off net positive trading fees, no rebate on rebates, only bonded DYDX counts)[^dydx-docs-2026-04-28-concepts-trading-rewards]. Per Nov 13, 2025 community vote, 75% of net protocol revenue is allocated to the Buyback Program (which acquires DYDX from market) — making DYDX the recipient of dYdX v4's largest single revenue stream[^dydx-community-2026-04-28-modules-distribution-protocol-revenue-sharing]. Full token page will be filed in Phase 2.2 at [[entities/token/dydx]].
